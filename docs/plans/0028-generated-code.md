# Plan: changes to the generated TypeScript

A review of what `dt generate ts` writes for `examples/shop` found seven points, and ADR 0027's T11 left two more
(contract tests for recursive types, contexts imported from another package), and one more was decided after
(infrastructure failures in the factories); the maintainer chose a solution for each. This plan records the choices and splits them into tasks. The decisions that change earlier ADRs (0001, 0020,
0023) are written down in a new ADR first (G0).

## Landing

- Starts on `main` after ADR 0027 (domain and application boundaries, #24): the generator lives in
  `capabilities/generation`, and these tasks work on that layout.
- As for ADR 0027: one integration branch from `main`, one worktree and branch per task, each done by a worker and
  merged into the integration branch after review, one pull request to `main`, squash merged.
- G1, G2, G5 and G6 break the code users write against the generated code; they ship in one release, with the breaking
  changes in the changelog.
- Every task leaves typecheck, lint, fmt, tests and build passing, and regenerates `examples/shop`, which stays
  consistent with the generated code (its own tests pass).

## Decisions

| # | Point | Decision |
|---|---|---|
| 1 | `UUID` is mapped to `string` and never checked: `makeCustomerId = (value) => value as CustomerId` accepts any string, though the model says `UUID` | An ID or primitive on `UUID` checks the form. `make<Name>` returns `Result<Name, Invalid<Name>>`, the violated invariant being `'uuid'`; the contract tests' arbitraries draw UUIDs |
| 2 | The check of each state repeats the aggregate's invariants (`checkDraftOrder`, `checkConfirmedOrder`, `checkCancelledOrder` each test the same three expressions) | A public `check<Aggregate>Common` checks the aggregate's invariants; the check of each state calls it and adds the state's. Return types and order are unchanged |
| 3 | Translated expressions are hard to read: `implies` as a double negation (`!(!(a) \|\| b)`), lambda variables as `$item`/`$item$`, string literals in `"…"` among `'…'` | All three: a violated `A implies B` is emitted as `A && !B`; lambda variables keep the names written in `.dt` (the second of a pair gets a suffix such as `item2`; a suffix is added only on a clash); string literals use `'…'` throughout |
| 4 | The target of `references` is only a trailing comment (`// -> Sales.Customer`) | The field's doc comment links it: `@see {@link Customer}` (`{@link Billing.Invoice}` across contexts). Types are unchanged |
| 5 | `_runtime.ts` (137 lines) and `tests/_testing.ts` (581 lines) are copied into every project | The runtime stays copied (production code does not depend on domaintrail). The testing support moves into domaintrail's package as the subpath `domaintrail/testing` (domaintrail is already a dev dependency); generated tests import it, and the generated code states the version it needs |
| 6 | The context of a verified type's factory with `for X?` is `context: X \| undefined`, so a call passes `undefined` explicitly | Kept. ADR 0023 and the factory's doc comment say why: an omitted context would compile, and the check would then not leave out the one it should (e.g. a customer's own address reported as taken) |
| 7 | Command parameters are positional (`place(id, customer)`, `cancel(order, reason)`); TypeScript has no named arguments, so parameters of one type can be swapped silently and reordering breaks callers | A command takes its parameters as one object, after the aggregate: `place({ id, customer })`, `cancel(order, { reason })`, and in a decision `Draft: (order, { reason }) => …`. A command without parameters takes none (`archive(order)`). Contract test inputs and examples become objects. The runtime cost (one small object per call) is negligible next to what a command allocates and the I/O around it |
| 8 | Recursive value types (allowed by M012 since ADR 0027's T11, which generates no contract tests for them) have no arbitraries | The contract tests draw recursive values with `fc.letrec`, biased towards shallow values (`depthSize: 'small'`), up to `generate.ts.tests.maxRecursionDepth` (default 4; a binary tree of depth 4 has at most 15 nodes), overridable per type (`tests.types["Ctx.Type"].maxRecursionDepth`, next to the existing arbitrary overrides). Cycles across several types are defined together. The guide says how to override the arbitrary of a type whose invariants reject too many drawn values |
| 9 | A context generated by another package cannot be used: `generate.ts.contexts.<Ctx>.out` writes a context elsewhere, but imports between contexts are relative paths, which cross package boundaries (ADR 0027). Found in ADR 0027's T11: Modeling's `.dt` copies the kernel's `Location` structurally | One repository keeps one configuration for all its contexts; a context written into another package names its module (`generate.ts.contexts.<Ctx>.module`, next to `out`), and generated code elsewhere imports it from there. This repository moves to one root configuration; the kernel describes itself in `.dt`, and Modeling uses its `Location` instead of a copy |
| 10 | How users are meant to handle infrastructure failures in the factories of verified types is unstated: a rejected promise escapes the `Result`, and TypeScript cannot type it | Stated, types unchanged: a rejected promise means the check could not be made (infrastructure); `Result`'s errors are the domain's (`errors`). As for policy handlers (ADR 0022), whose rejected promise means the input cannot be computed now. ADR 0028 amends ADR 0023; the factory's doc comment says it; the guide shows a use case handling a rejection at its edge |
