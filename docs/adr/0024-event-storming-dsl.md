# ADR 0024: The Event Storming DSL (`.dtes`) — architecture of v0.1

- Status: accepted. Three choices the spec leaves open were decided by the maintainer: storming IDs unique in the
  workspace, the hotspots of a timeline filter, and the default `sources` (marked *Decided by the maintainer*).
- Date: 2026-10-31
- Spec: [docs/dtes-v0.1.md](../dtes-v0.1.md). Its semantics, the sections marked 確定 in particular, are the reference.
  This ADR fixes only how they are implemented, plus the details the spec leaves to "実装調査" (§13, §14).

## Context

The spec adds a second, independent text DSL to the repository. It defines `storming` blocks of events, commands,
policies, actors, external systems, aggregates, read models, hotspots, timelines and groups, with optional
fully-qualified `ref`s to `.dt` symbols. It also defines two independent view axes: Big Picture / Design Level, and
the integrated canvas / one timeline. It asks that the implementation reuse what exists (§13–§14) and that `.dt` stays
unchanged.

This ADR records what exists, how `.dtes` fits into it with the smallest change, and the contract between the tasks
that build it in parallel (T2–T8). The shared types are in `src/dtes/ir.ts`.

## Decision

### Parser: a second Langium language in the same project

- `src/dtes/storming.langium`, `grammar EventStorming`, added to `langium-config.json` as a second language
  (`"id": "dtes"`, `"fileExtensions": [".dtes"]`). `projectName` and `out` (`src/language/generated`) stay as they
  are. Generation then adds `EventStormingGrammar`, `EventStormingLanguageMetaData` and `EventStormingGeneratedModule`
  next to the `.dt` ones. `DomainGeneratedSharedModule` (one `AstReflection` for both) serves both languages.
- **Every rule and type of the grammar starts with `Es`** (`EsFile`, `EsStorming`, `EsEvent`, `EsClause` …): the
  combined `ast.ts` then never collides with `.dt` names, and `isEsCommand` reads apart from `isCommand`.
- **Terminals are copied verbatim** from `domain.langium` (`WS`, `STRING`, `ID`, `ML_COMMENT`, `SL_COMMENT`; not
  `INT`/`DECIMAL`, which are unused). `domain.langium` is not touched: a shared imported terminals file would edit the
  `.dt` grammar for no gain. A test compares `Domain.Terminals` with `EventStorming.Terminals` in the generated
  `ast.ts`, so the copies cannot drift (spec §14 item 1). Escapes, comments and `///` doc comments are therefore the
  same as in `.dt`.
- The grammar is **permissive where that gives better messages**. Every element may have a `{ … }` body, and every body
  accepts every clause (`ref`, `actor`, `reads`, `target`, `emits`, `on`, `issues`, `status`, `resolution`). Which
  clause an element may have, how many, and the kinds of their targets are checked by the validator (S004–S006, S003).
  `status` takes an `ID`, checked by S009. A timeline body accepts event IDs and `group`s only, and a group accepts
  event IDs only, at least one; anything else there is `SYNTAX` ("不正なブロック").
- `ref` paths are `ID ('.' EsName)*`, where `EsName` also accepts the `.dtes` keywords, because a `.dt` command may be
  named `target` or `status`.
- Local references (`target Shipment`, timeline steps) are Langium cross-references to any declaration of the
  enclosing storming (`[EsDeclaration:ID]`, scoped by a scope provider in `src/dtes/language/module.ts`). They resolve
  whatever the kind, so the LSP has go-to-definition, references and rename, and a wrong kind becomes S003 with a
  precise message instead of a linking error. Langium's own linking diagnostics are dropped. S002 and S003 are
  reported from the storming IR.
- `.dt` `ref`s are **not** Langium cross-references. `.dt` exports only context elements, not commands
  (`DomainScopeComputation`), and changing that would change `.dt` scoping. They are strings resolved by the linker
  against the Typed Model (T4).
- **The storming IR** (`Storming` in `src/dtes/ir.ts`) is built from the AST after parsing. It holds every clause as
  written, invalid ones included, with source ranges. The validator, the linker and the projection work on it alone,
  never on the AST, so they can be built and tested apart from the parser.
- **tree-sitter and Zed are out of v0.1.** The Langium grammar is the reference (CONTRIBUTING). A second
  tree-sitter grammar needs the wasm build, a new build stamp and a new Zed `rev`. Highlighting is the only thing it
  would add, while `dt lsp` already gives editors diagnostics, navigation and formatting for `.dtes`. It is a
  follow-up.

### Workspace and CLI: the same `dt`, the same sources

- *Decided by the maintainer:* `DEFAULT_SOURCES` becomes `['**/*.dt', '**/*.dtes']`. A config that sets `sources` lists a
  `.dtes` glob itself (`"sources": ["domain/**/*.dt", "domain/**/*.dtes"]`); the guide says so. `findDomainFiles`,
  `SourceScope`, the watcher, the LSP's `DomainWorkspaceManager` and the git baseline's `sourcesAt` then find `.dtes`
  files with no change of their own. The extension decides the language (`isStormingFile(path)`: `.dtes`).
- `analyze(sources)` splits the sources by extension. The `.dt` sources go through today's pipeline unchanged. The
  `.dtes` sources go through `analyzeStormings(stormingSources, model)` with the Typed Model of the `.dt` sources (or
  `undefined` when they do not parse). `Analysis` gains `stormings: StormingAnalysis`. Its diagnostics are merged into
  `Analysis.diagnostics`, sorted by `compareDiagnostics`. `syntaxOk` and `model` keep their `.dt` meaning, so a broken
  `.dtes` never hides the domain model in the Live View. `ok` also counts the `.dtes` errors.
- **`dt check`** checks both, and `--format json` carries both in the same `diagnostics` array. The exit code is 1 on
  any error. A workspace with only `.dtes` files is valid (UC1 starts from events), so the no-files error becomes "No
  .dt or .dtes files found". `summary.files` counts both.
- **`dt generate ts`** writes from `.dt` only. It refuses on `.dt` errors as today and is not blocked by `.dtes` errors:
  a storming is exploration, and §5.3 keeps the two decoupled. It reports `.dtes` diagnostics like `check`.
- **`dt fmt`** formats `.dtes` files with `formatStorming` (T2), chosen by extension. The rules are in the same spirit
  as `dt fmt`: 2 spaces, one clause per line, an element without clauses on one line, comments kept.
- **`dt view`** and **`dt lsp`** pick `.dtes` up through the shared pipeline (below). There is no new subcommand and no
  new flag: spec §14 asks for no separate CLI product, and every existing command already takes the workspace root and
  config.
- `dt show` stays `.dt` only in v0.1 (follow-up).

### Diagnostics: rule prefix `S`

The spec's numbers are proposals (§11). `.dtes` rules take the prefix `S` (storming): `E` would read as "error", and
`ES01`… are the spec's acceptance-test names. Syntax errors of `.dtes` files are `SYNTAX`, as for `.dt`. The `RuleId`
union already lists them (`src/core/diagnostics.ts`), and the guide's Rules table has a row for each (a test requires
it; `dt guide S001` works). T6 changes the schema's `code` pattern to
`^(SYNTAX|[MLS]\d{3})$`, and its description of `summary.files` and `file` to cover `.dtes`.

| Rule | Spec §11 row | Condition | Severity | Owner |
|---|---|---|---|---|
| S001 | Symbol | Two declarations of a storming with the same ID, of any kinds (groups and timelines included). *Decided by the maintainer:* two stormings with the same ID in the workspace. | error | T3 |
| S002 | Symbol | A local reference (relation target, timeline/group step) names no declaration of its storming | error | T3 |
| S003 | Kind | A reference to a declaration of the wrong kind: `target` not an aggregate, `reads` not a read model, `actor` not an actor/external, `emits`/`on` not an event, `issues` not a command, a timeline or group step not an event (ES02, ES14) | error | T3 |
| S004 | Cardinality | More than one `target`, `ref`, hotspot `on`, `status` or `resolution` on one element (ES03) | error | T3 |
| S005 | Cardinality | `ref` on an element that may not have one: policy, actor, external, read model, hotspot (ES13) | error | T3 |
| S006 | Syntax ("未知の関係") | A clause the element kind does not take (`target` in a policy, `status` in a command, any relation on an event, aggregate, actor, external or read model) | error | T3 |
| S007 | Group | The same event twice in one group (ES11) | error | T3 |
| S008 | Policy | A policy without `on` or without `issues` (ES05) | error | T3 |
| S009 | Hotspot | A `status` other than `open`/`resolved`, `resolved` without `resolution`, `resolution` without `status resolved` (ES08) | error | T3 |
| S010 | `.dt ref` | A `ref` that is not fully qualified for its element (`Ctx.Event`, `Ctx.Aggregate`, `Ctx.Aggregate.command`) or names nothing in the `.dt` model (hint: `didYouMean`) | error | T4 |
| S011 | `.dt ref` | A `ref` to a `.dt` symbol of the wrong kind (an event's `ref` naming an aggregate …) | error | T4 |
| S012 | `.dt` contract | A command's `ref` names a command of another aggregate than the `ref` of its `target` | warning | T4 |
| S013 | `.dt` contract | A command `emits` an event that the `.dt` command provably never emits (below) | warning | T4 |
| S014 | Graph | A type-level cycle Policy → Command → Event → Policy. The message says it is a cycle of possibilities, not an infinite loop | warning | T3 |

- **Not implemented in v0.1:** the optional Info rule (a policy with ≥2 `on` and ≥2 `issues`). The spec marks it 任意,
  and it would need a third severity through `Diagnostic`, the schema, the CLI summary and the LSP. The guide states
  instead that such a policy carries no Cartesian meaning (T8). Not diagnosed, as the spec says: timeline order
  against causality, completeness, missing `emits`, read models without a `.dt` counterpart, and cross-context
  policies.
- When the `.dt` sources do not parse (`Analysis.model` absent), S010–S013 are skipped rather than guessed.
- `.dtes` diagnostics carry `elementId: esElementId(storming, localId)` (`es/<Storming>/<Local>`): a namespace of its
  own, so it never collides with `.dt` IDs (`Sales.Order`, `Sales.Order:confirm`).
- The validator and the linker report from IR ranges with `esDiagnostic(...)`, not with `DiagnosticSink`, which needs
  AST nodes.

### `.dt` symbol resolution for `ref`

The linker resolves a `ref` against `DomainModel` (`analysis.model`), not the AST:

| `.dtes` element | Path | Resolves to | Kind check |
|---|---|---|---|
| `event` | `Ctx.Name` (2 segments) | `model.elements['Ctx.Name']` | `kind === 'event'` |
| `aggregate` | `Ctx.Name` (2 segments) | `model.elements['Ctx.Name']` | `kind === 'aggregate'` |
| `command` | `Ctx.Aggregate.command` (3 segments) | `model.elements['Ctx.Aggregate'].commands.find(c => c.name === 'command')` | the element is an aggregate and has the command |

- A wrong number of segments is S010 ("not fully qualified"). Nothing is resolved by simple name or by guessing a
  context (§2). An existing element of another kind, or an aggregate without the command, is S011. A missing element
  is S010, with `didYouMean` over the qualified names of the right kind (`src/core/suggest.ts`).
- A `.dt` `policy`, value type or error is never a valid target. The `.dtes` policy may not have a `ref` at all.
- Missing `ref`s are never diagnosed (§2, ES07).

### Contract warnings (§14 item 4)

`.dt` `emits` is exact and exhaustive (ADR 0018, generated as the `events` record and `NoEvents`). A `.dt` command
never emits an event it does not list, and emits nothing on failure. So exactly one mismatch is provable:

- **S013**: command `C` has a resolved `ref` to `.dt` command `K`, `C` has a valid `emits E`, `E` has a resolved `ref` to
  `.dt` event `X`, and `X` is not among `emittedEvents(K)` (any multiplicity, any `when`). The warning says that the
  `.dt` contract of `K` never emits `X`. Its hint suggests adding `X` to `K`'s `emits` (or, for a failure outcome, an
  error of `K`) or correcting the `ref`.
- Nothing else about `emits` is diagnosed. An event `K` emits that `C` does not list, a `.dtes` `emits` whose event has
  no `ref`, and a different multiplicity or `when` are not, since `.dtes` describes possibilities partially (§5.2).
- **S012**: `C` has a resolved `ref` `Ctx.Agg.cmd`, and its (single, valid) `target` has a resolved `ref` other than
  `Ctx.Agg`.

### Projection: semantic graph, occurrences, prefix trie, render graph

These are pure functions of the storming IR (T5), with the types in `src/dtes/ir.ts`:

- `buildSemanticGraph(storming)` keeps each valid relation once (`RELATION_RULES`; a resolved target of an allowed
  kind), directed as in §9.1, and never infers an edge (R09).
- Each timeline becomes `Step`s (`stepOf`: a group's events sorted and deduplicated) and its `EventOccurrence`s
  (`stepPath` `[i]` or `[i, j]`, kept from the source). A prefix trie over the timelines is keyed by `stepKey`, and its
  children are ordered by key, not by declaration, so the trie does not depend on timeline order (R06).
- **Render node IDs** are path-derived, which keeps them stable under append (R07):
  - `t:<keys from the root joined by '>'>` for a trie node: an event node, or a group node whose members are
    `t:…/<eventId>`;
  - `e:<eventId>` for an event in no timeline;
  - `n:<localId>` for every other element.

  `matchRenderNodes(previous, next)` pairs the nodes of two render graphs of one view across an edit (same event and
  matching neighbouring steps). It leaves ambiguous ones unpaired (R08, §10.3), and the layout uses the pairs as
  position hints.
- Edges: a render edge `semantic` points back to its semantic edge (`semanticEdgeKey`). It is drawn once per render
  node of its event, so one semantic edge may be drawn several times, and no semantic edge is ever added. A `sequence`
  edge joins consecutive steps of the trie (to and from a group node, never inside it), so groups have no inner order
  (R04).
- **Integrated canvas**: the whole trie, the `e:` nodes of events in no timeline (R15), and the other elements of the
  level with their semantic edges.
- **Timeline filter** (§9.3): the selected timeline's trie path, which is a chain, plus each 1-hop path
  `Event → Policy → Command → Event` whose two events occur in that timeline, with the actors, read models and target
  of those commands. There are no multi-hop paths and nothing outside the timeline (R16).
- *Decided by the maintainer:* with a filter, a hotspot is shown when its `on` event occurs in the selected timeline, at
  both levels. A hotspot without `on` is shown only on the integrated canvas. This includes everything §9.3 lists,
  keeps hotspots visible in Big Picture (§6) and adds no causal edge.
- **Levels**: `LEVEL_KINDS`. Big Picture keeps events, timeline order, groups, hotspots and `hotspot-on` edges.
  Design Level adds the rest, `external` included (R17). Events are never dropped (R14).
- The graph is cyclic-safe: every element is one node, and the trie is finite (R10).

### Rendering: the existing graph, layout and Live View

- `renderToGraph(render, storming)` (T7, `src/dtes/view/graph.ts`) converts a `RenderGraph` into the existing `Graph`
  IR. Its node kinds are `esEvent`, `esCommand`, `esPolicy`, `esActor`, `esExternal`, `esAggregate`, `esReadModel`,
  `esHotspot` and `esGroup` (a container whose children are its event nodes). Its edge kinds are `esCausal` (solid,
  directed), `esRelated` (dotted) and `esSequence` (dashed). These kinds are added to `NodeKind`/`EdgeKind` in
  `src/graph/ir.ts`. The label is the element's label, its ID in name mode, and both in both mode. The stereotype is
  the kind. The `.dt` `ref` and the occurrences with their timelines go to the inspector (§6, §8.4).
- Layout uses the existing `ElkLayoutEngine`, with direction `RIGHT` for graph IDs with the prefix `storming`
  (`DIRECTION` in `src/layout/elk.ts`). Graph ID: `storming:<StormingId>:<level>:<timelineId or *>`. **Canonical
  layout**: the render graph's nodes and edges are sorted (`RenderGraph` is canonical), ELK runs with the existing
  model-order options and fixed seed, and the same storming, view and engine give the same layout. **Incremental
  layout**: the existing signature cache keeps an unchanged graph's layout. For a changed one, the positions of the
  nodes paired by `matchRenderNodes` seed ELK's interactive/semi-interactive strategies. Should that not keep the
  timeline order (§10.2's first priority), v0.1 ships canonical layout only and records incremental layout as a
  follow-up. Positions are never written to `.dtes`, only to `.domaintrail/layout.json` like every layout.
- No new drawing library. tldraw shapes in `web/shapes.tsx` get the new kinds. The spec's colours are defaults, with
  sufficient contrast in both themes.
- Server: `ViewPayload.stormings` holds per storming its ID, label, file, timelines (ID, label), the `Storming` IR
  for the inspector, and a graph for every view (`VIEW_LEVELS` × (integrated + each timeline)), all precomputed like
  the state views. The key is `<level>|<timelineId or empty>`. There are few views, and toggling then needs no round
  trip. A workspace with `.dtes` files only is not `empty`.
- Web: a fourth view kind `storming` (picker of stormings), with a level toggle and a timeline select as UI state,
  kept like the other view settings (local storage), never in the DSL (R11, R12).

Dependencies: T3, T4 and T5 depend only on `src/dtes/ir.ts`, and their tests may build IR by hand until T2 lands.
T6 needs T2–T4 to integrate, T7 needs T5 (and T6's `Analysis.stormings`), and T8 needs the commands to exist.

## Consequences

- `.dt` grammar, scoping, checkers and generated code are unchanged. The generated `ast.ts` grows by the `Es*` types.
- Existing configs with explicit `sources` see no `.dtes` until they add a glob. The default sees both.
- `dt check` fails on `.dtes` errors, `dt generate ts` does not.
- Follow-ups: tree-sitter/Zed support, `dt show` for stormings, change marks for stormings against a baseline, the
  Info rule (with a third severity), drawing one occurrence in two places (§7.3), and incremental layout if it does not
  make v0.1.
