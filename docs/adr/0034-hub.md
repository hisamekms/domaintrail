# ADR 0034: The hub — a project's collaboration hosted on Cloudflare, with a device that runs the AI

- Status: **proposed (draft)**. The decisions marked *Decided by the maintainer* were taken in a design discussion on
  2026-11-07; the rest is *Proposed* or listed under [Open questions](#open-questions), which must be settled before
  this ADR is accepted. Nothing is implemented.
- Date: 2026-11-07
- Input: a request from users (2026-11-07):
  1. host DomainTrail on Cloudflare;
  2. read the published Event Storming and domain model;
  3. each project readable by its members only;
  4. the connection to Claude Code and live editing happen by connecting the hosted part to the local machine of one
     specific device.
- Builds on: [ADR 0026](0026-collaboration-sessions.md) (sessions, Access, the agent API),
  [ADR 0027](0027-domain-and-application-boundaries.md) (contexts, capabilities, platform, apps),
  [ADR 0031](0031-knowledge.md) (knowledge, the `cloudflare` store, projects and members, `dt publish`),
  [ADR 0033](0033-people-edit-stickies.md) (people edit stickies without an AI run).

## Context

What `main` already has, against the four requests:

| Request | On `main` | Missing |
|---|---|---|
| Hosted on Cloudflare | `apps/knowledge-worker`: a Worker with D1, R2 and Access that the user deploys (ADR 0031 §5) | it holds knowledge only; sessions run on the facilitator's machine |
| Published ES | `dt publish` (run by CI when `main` changes) → the `published` table → a read-only page (ADR 0031 §11) | — |
| Published domain model | — | `.dt` views are not published |
| Members only | `projects.visibility` and `project_members` exist; `authorize` allows everyone (ADR 0031 §6) | enforcement, member management, sessions narrowed the same way |
| Live editing from a device | `dt collab` on the facilitator's machine, reached through a quick tunnel (`link` mode) or Access | a hosted entry point; chat and AI history exist only in that machine's `session.db` |

In the discussion the maintainer also asked that **knowledge, chat and the AI's work history stay readable while the
device is offline**, and that a lost local database must not lose them.

Two facts from the code shaped the decisions:

- The session's state is not tied to files: the chat, requests, proposals, approvals, votes, the journey, knowledge
  and the run queue are records of who said and decided what. What is tied to the device is the workspace (`.dt`,
  `.dtes`, git) and the processes (Claude Code, `dt fmt`/`dt check`).
- After ADR 0027 the `domain/` and `application/` layers of `contexts/collaboration` and `contexts/knowledge` import
  `node:` only in tests, and the parsers and the layout need little of Node (`node:path` in the two `parse.ts`,
  `createRequire` in `capabilities/visualization/src/adapters/elk.ts`). The application layer can run on Workers
  behind other adapters.

## Decision

### 1. Each team deploys its own hub

*Decided by the maintainer.* DomainTrail ships the hub as a template the user deploys to their own Cloudflare account,
as `apps/knowledge-worker` is today: one deployment per organisation, no shared SaaS, dt creates nothing in Cloudflare.
*Proposed*: the knowledge Worker grows into the hub (`apps/hub`); its D1 schema and the read-only page are kept and
migrated, not rebuilt.

### 2. Authentication by Access, authorization by the hub's members

*Decided by the maintainer.* One Access application in front of the whole hub proves who a person is (one-time PIN or
the organisation's identity provider; the JWT verification of ADR 0026 S8 is reused). Who may do what in a project is
the hub's own data in D1: `project_members`, enforced by `authorize(user, project, action)` on every route, page, socket
and stored object (published forms, knowledge, history, revisions, images). Access applications per project are not
used: they cannot be managed from the hub and cannot see who acts through dt's token.

*Decided by the maintainer*: three roles per project.

| Role | May |
|---|---|
| `owner` | everything a member may, and manage members, register devices, import and export |
| `member` | join sessions, write in the chat, send requests, edit stickies, correct and delete knowledge |
| `viewer` | read the published forms, the working state, knowledge and the history; write nothing |

The facilitator stays a role inside a session (ADR 0026), not a project role. A project with `visibility: members`
admits nobody else, and joining its sessions is narrowed the same way (ADR 0031 §6).

### 3. The hub is the source of truth for collaboration and for the session's workspace

*Decided by the maintainer*, after comparing a hub that only relays to the device, a device that replicates to the hub,
and a tunnel per device (see [Alternatives](#alternatives-considered)).

| State | Source of truth |
|---|---|
| chat, requests, proposals, approvals, votes, marks, the journey, knowledge, the run queue | the hub |
| presence (cursors) | the hub, ephemeral (never reaches the device) |
| the session's `.dt`, `.dtes`, `domaintrail.jsonc` and journey files, and their revisions | the hub (revisions' blobs in R2) |
| the repository and its git history, the application code | git, on developers' machines |
| running Claude Code (runner, answerer, extractor), with access to the code | the device |

Consequences the maintainer accepted with it:

- Everything stays readable when the device is offline, and a lost device loses nothing: another device connects and
  takes over. The "copy the hub back to the local database" feature asked for earlier is not needed.
- Deleting personal data happens in one place; the redaction log of ADR 0031 §7 remains only for local sessions.

### 4. The device runs the AI, and only that

*Proposed*, following §3. A registered device connects out to the hub (no inbound port, no tunnel) and claims work as
the subscriber of ADR 0026 does today: SSE or WebSocket, a claim with a lease, a heartbeat, an idempotent completion
keyed by run and lease token. For a run it materialises the hub's DSL files over a worktree of the import's base commit
(so the AI can read the code), runs Claude Code, and returns the changed files; the hub validates them and records a
revision. While no device is connected, the hub accepts writes and shows that the AI is not connected; runs and answers
wait.

### 5. git is reached by import and export through dt

*Decided by the maintainer.*

- Features that need git history (the baseline at any git ref, `/api/git/refs`) are **local-server only**. In the hub,
  comparisons are between the hub's revisions, or against the published form.
- `dt` imports the DSL files of a commit into the hub and records that commit's SHA as the **base**.
- `dt export` writes the hub's files **on a new branch cut from the base SHA** and commits them; the merge into `main`,
  and any conflict with what `main` gained meanwhile, go through git and a pull request. The commit message carries the
  session's record (*Proposed*).

### 6. The hub parses, checks and lays out

*Decided by the maintainer.* Parsing, `dt check` and the layout run in the hub (Worker or Durable Object), so that the
working state can be shown, people can edit stickies (ADR 0033) and changes can be validated while no device is
connected. *To verify before acceptance*: removing the `node:` uses named in the Context, and that the layout of the
largest known models fits the Worker's CPU limit; if it does not, the layout alone moves to the browser.

### 7. "Published" means what is on `main`

*Decided by the maintainer.* The published forms remain what CI publishes with `dt publish` when `main` changes, so a
published drawing has always been reviewed; `dt publish` is extended from stormings to the `.dt` views. The hub's
working state is a separate thing, readable by members at any time.

### 8. The local server stays

*Decided by the maintainer* (git features are local-server only, §5). `dt collab` without a hub keeps working on
`node:sqlite`. *Proposed*: the collaboration and knowledge application layers are shared, with storage adapters for
`node:sqlite` and for the hub (Durable Object SQLite, D1, R2), and the same contract tests run against both.

### Shape (*Proposed*)

```
Cloudflare (the team's account)                         a registered device
 Worker: pages, API, authorize(), Access JWT             dt connect
 D1: users, projects, members, devices, knowledge,  ◀──  ├ claims runs/answers/extractions (outbound only)
     published forms                                     ├ worktree at the base SHA + the hub's DSL files
 Durable Object per project: the session (SQLite),       └ Claude Code
     presence, the run queue, the working files
 R2: revision blobs, images
```

## Alternatives considered

- **The hub relays only; all state stays on the device.** Smallest change, but nothing is readable while the device is
  offline, and the history is lost with the device. Rejected by the maintainer.
- **The device stays the source of truth and replicates to the hub** (the outbox shipped to the hub, a restore from the
  hub to a new device). Offline reading works, but every participant's write must still be forwarded to the device as
  a command, the git and comparison reads need calls back to the device, and two copies must be kept consistent.
  Superseded by §3 when the maintainer asked whether the hub should not simply be the source of truth.
- **A tunnel per device, the hub only linking and authorizing.** Reuses `--tunnel` and Access, but URLs change with the
  device, Access must cover each device's hostname, and offline reading would still need a second path.
- **Workers reaching a device's tunnel privately (Workers VPC and the like).** Keeps one URL, but still makes the
  device the server; not needed once the hub is the source of truth.
- **Access applications per project.** See §2.
- **Publishing a revision from the hub.** Faster than waiting for `main`, but the published form could differ from
  `main` and skip review. The maintainer chose `main` (§7).

## Consequences

- The hub becomes a product DomainTrail versions: a template with D1 migrations, a Durable Object class, R2 buckets,
  and an upgrade path from `apps/knowledge-worker`.
- The collaboration and knowledge contexts get a second set of storage adapters, and their tests run twice.
- `dt` gains `connect` (a device), import and `export` against a hub; the web app talks either to the local server or
  to the hub, with git features hidden in the hub.
- The facilitator's machine is no longer required for a session to exist, only for the AI to work.

## Open questions

1. **Who is the primary user**, and so **how long the hub's workspace lives.** One continuous workspace per project
   (sessions are periods over it; export at any time; import refused while there are unexported changes, unless
   discarded explicitly) suits business people who come back to the working state between sessions. One workspace per
   session (import at start, export at end) suits developers who treat `main` as the only lasting state. The maintainer
   noted that the answer depends on which of them is the main target.
2. **People's edits while a run runs.** A run starts from a revision; if the hub moved on meanwhile (ADR 0033 edits),
   its result must be merged, re-applied (as ADR 0033 does locally) or refused.
3. **Devices.** How a device is registered and authenticated (a revocable per-project device token issued by an owner
   is the proposal; Access service tokens are organisation-wide), whether several devices may serve one project, and
   which one claims.
4. **Access and invitations.** Members, including business viewers, must pass the Access policy before the hub's
   membership applies: an allow rule per e-mail kept in sync by the hub, a broad rule (an e-mail domain, one-time PIN
   for everyone) with D1 as the real gate, or groups of the identity provider.
5. **Migration.** From `apps/knowledge-worker` (data and URL), from the `files` knowledge store, and whether a local
   `session.db` can be uploaded to a hub.
6. **Writes while no device is connected.** Accepted and queued (§4); a limit on how long a request may wait, and what
   people see meanwhile.
7. **The import's scope.** Which files the hub holds (the DSL sources and the journey only is the proposal), and how
   an AI run that changes something outside them is treated.
