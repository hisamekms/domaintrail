# ADR 0028: Changes to the generated TypeScript

- Status: accepted, not implemented (G1–G8 of [the plan](../plans/0028-generated-code.md), on `feat/generated-code`).
  Every decision below was chosen by the maintainer among the alternatives listed with it (marked *Decided by the
  maintainer*).
- Date: 2026-11-02
- Input: the code on `main` at `b874923` (#24, ADR 0027, merged), and what `dt generate ts` writes for `examples/shop`
  there. The shapes quoted as "today" are that output.
- Amends: [ADR 0001](0001-mvp-implementation-decisions.md), [ADR 0003](0003-domain-primitives.md),
  [ADR 0020](0020-generated-checks-and-contract-tests.md), [ADR 0023](0023-verified-types.md) and
  [ADR 0027](0027-domain-and-application-boundaries.md); see [Amends](#amends).

## Context

A review of what `dt generate ts` writes for `examples/shop` found seven points in the generated code: IDs on `UUID`
that are never checked, the aggregate's invariants repeated in the check of every state, translated expressions that
are hard to read, the target of `references` only in a trailing comment, two support files copied into every project,
a context parameter that must be passed as `undefined`, and command parameters by position. ADR 0027 left two more
(T11): contract tests for recursive types, and a context generated by another package, which cannot be used. A tenth
was raised after: how the factories of verified types report a failure of the infrastructure, which ADR 0023 does not
say.

The users of the generated code are people and, more often, AI agents implementing against it. What the types and the
checks say is what they follow; what a comment says is what they miss (ADR 0023). Every point below is judged by that.

Three of the changes (decisions 1, 5 and 7, tasks G1, G5 and G6) break code written against the generated code. They
ship in one release, with the breaking changes in the changelog, so that users migrate once.

## Decision

### 1. An ID or domain primitive on `UUID` checks the form

**Today.** `UUID` maps to `string` (ADR 0001) and nothing checks it. An ID without invariants has a constructor that
cannot fail (ADR 0003) and accepts any string, though the model says `UUID`:

```ts
export type CustomerId = string & { readonly __domain: 'Sales.CustomerId' };
export type MakeCustomerId = (value: string) => CustomerId;
export const makeCustomerId: MakeCustomerId = (value) => value as CustomerId;
```

`examples/shop` makes IDs such as `makeCustomerId('customer-1')` (`fixedProviders`, `src/contract.test.ts`); they
compile and run. The contract tests draw `fc.uuid()` for the arbitraries of such IDs, but test `makeCustomerId` with
`invariants: []`, so every string is expected to be accepted.

**Decision.** *Decided by the maintainer:* an ID or a domain primitive whose base is `UUID` checks the form. Its
constructor is generated like that of a primitive with invariants: the form is an invariant named `'uuid'`, and
`make<Name>` returns `Result<Name, Invalid<Name>>`.

```ts
export interface InvalidCustomerId {
    readonly type: 'InvalidCustomerId';
    readonly value: string;
    /** The violated invariant. */
    readonly invariant: 'uuid';
}
export type MakeCustomerId = (value: string) => Result<CustomerId, InvalidCustomerId>;
export function checkCustomerId(value: string): readonly InvalidCustomerId['invariant'][] { … }
export const makeCustomerId: MakeCustomerId = (value) => { … }; // err({ type: 'InvalidCustomerId', value, invariant: 'uuid' })
```

- The type is unchanged (`string & { readonly __domain: … }`); a plain field or parameter of type `UUID` stays
  `string`, unchecked, like `String` (a plain field has no constructor to check it in).
- The contract tests keep drawing UUIDs for these types, now filtered by the check like any primitive with invariants,
  and T1 (ADR 0020) tests `make<Name>` with UUIDs and other strings: it must accept exactly the UUIDs (and, with other
  invariants, those that hold them too) and report `'uuid'` for the others.
- `examples/shop` makes its IDs from UUIDs (its fixed providers included), and the guide and getting-started pages
  show `make<Id>` returning a `Result`.

**Why.** The model says `UUID`; a value that is not one should not become an ID silently, and an agent writing
`makeOrderId('order-1')` in a fixture should be told so by the compiler (the `Result`) and at run time (the error).
One constructor that checks, as for every other primitive, keeps one path to a value of the type.

**Compatibility.** Breaking (G1): every call of `make<Id>` on a `UUID` base now handles a `Result`, and IDs that are not
UUIDs (fixtures, readable test IDs) are rejected.

**Rejected.**

- An unchecked `make` kept, with a separate `parse` that checks: two paths to the same type, and the reader must know
  which one the value went through; the unchecked one is the one an agent picks.
- Saying it in the documentation only (`UUID` documents the intended form): the model and what users write disagree,
  and nothing reports it.
- Configurable strictness (a setting for checked or unchecked UUIDs): every combination of settings is a variant of the
  generated code and of the tests to keep working.

### 2. `check<Aggregate>Common`: the aggregate's invariants checked once

**Today.** The check of each state repeats the aggregate's invariants. For `Sales.Order`, `checkDraftOrder`,
`checkConfirmedOrder` and `checkCancelledOrder` each test the same three expressions before their state's own:

```ts
export function checkCancelledOrder(order: CancelledOrder): readonly ('quantitiesPositive' | 'distinctSkus' | 'singleCurrency' | 'otherNeedsNote')[] {
    const violated: ('quantitiesPositive' | 'distinctSkus' | 'singleCurrency' | 'otherNeedsNote')[] = [];
    if (!(order.items.every(($item) => ($item.quantity > 0)))) violated.push('quantitiesPositive');
    if (!(distinct(order.items, ($item, $item$) => $item.sku === $item$.sku))) violated.push('distinctSkus');
    if (!(order.items.every(($a) => order.items.every(($b) => ($a.unitPrice.currency === $b.unitPrice.currency))))) violated.push('singleCurrency');
    if (!(!(order.reason === "Other") || (order.note !== undefined))) violated.push('otherNeedsNote');
    return violated;
}
```

**Decision.** *Decided by the maintainer:* a public `check<Aggregate>Common` checks the aggregate's invariants, on its
common fields; the check of each state calls it and adds the state's. Return types and the order of the violated
invariants are unchanged.

```ts
export function checkOrderCommon(order: OrderCommon): readonly ('quantitiesPositive' | 'distinctSkus' | 'singleCurrency')[] { … }
export function checkCancelledOrder(order: CancelledOrder): readonly ('quantitiesPositive' | 'distinctSkus' | 'singleCurrency' | 'otherNeedsNote')[] {
    const violated: ('quantitiesPositive' | 'distinctSkus' | 'singleCurrency' | 'otherNeedsNote')[] = [...checkOrderCommon(order)];
    if (order.reason === 'Other' && !(order.note !== undefined)) violated.push('otherNeedsNote');
    return violated;
}
```

It exists where `<Aggregate>Common` does — an aggregate with states — and the aggregate has invariants of its own. An
aggregate without states keeps `check<Aggregate>`, which already is that check. With invariants declared without an
expression it takes the `…With` form of ADR 0020 (`check<Aggregate>CommonWith(checks)`), like every check with slots.

**Why.** One translation of each invariant, read once; and users can check the common part alone.

**Compatibility.** Additive (G2): a new export; the existing checks return the same values.

**Rejected.**

- A private helper shared by the state checks: the same output, but users cannot check the common part alone.
- Leaving it as it is: the repetition grows with every state, and a reader compares the copies to see they are the
  same.

### 3. Readable expressions: `implies`, lambda names, quotes

**Today.** Three things make the translated expressions hard to read (see the code above):

- a violated `A implies B` is a double negation: `!(!(A) || B)`;
- lambda variables are renamed `$item`, and the second of a pair (in `unique`) `$item$`;
- string literals are written with `JSON.stringify`, in `"…"`, among the generator's `'…'`. In `examples/shop` the
  `"Other"` above is an enum member, which is written the same way.

**Decision.** *Decided by the maintainer:* all three.

- A violated `A implies B` is emitted as `A && !B`, where the check tests the violation (an invariant or a
  requirement whose expression is the implication). Inside a larger expression the implication keeps its form
  `!A || B`.
- Lambda variables keep the names written in `.dt`: `(item) => item.quantity > 0`, `(a) => … (b) => …`. The second of
  a pair gets a suffix: `(item, item2) => item.sku === item2.sku`. A suffix is added only on a clash.
- String literals use `'…'` throughout the generated code, enum members included.

```ts
if (!(distinct(order.items, (item, item2) => item.sku === item2.sku))) violated.push('distinctSkus');
if (order.reason === 'Other' && !(order.note !== undefined)) violated.push('otherNeedsNote');
```

**Why.** The checks are the translation of the model that agents and people read next to the JSDoc; they should read
like the `.dt` they come from.

**Compatibility.** Same behaviour (G3): the text of the checks changes, not what they return.

**Rejected.**

- Only the double negation: the names and quotes still read as machine output.
- Running a formatter over the output: it does not rename variables or rewrite negations, and adds an external tool to
  generation.
- Leaving it as it is.

### 4. `{@link}` to the target of `references`

**Today.** The target of `references` is a trailing comment, which editors do not resolve:

```ts
    /** 顧客 */
    readonly customer: CustomerId; // -> Sales.Customer
```

**Decision.** *Decided by the maintainer:* the field's doc comment links the target, by the name the module uses for it:
`@see {@link Customer}` in its context, `{@link Sales.Order}` from another (`Billing.Invoice.order`). The trailing
comment goes. Types are unchanged.

```ts
    /**
     * 顧客
     * @see {@link Customer}
     */
    readonly customer: CustomerId;
```

**Why.** Hover and go-to-definition reach the aggregate the field points at, and the link is renamed with it.

**Compatibility.** Same behaviour (G4).

**Rejected.**

- A type that carries the target (`Ref<CustomerId, 'Customer'>`): the field then differs from the ID it holds, and every
  read and write converts between them.
- Leaving it as it is.

### 5. The testing support becomes a package, `@domaintrail/testing`

**Today.** Two support files are written into every project, the same for every model: `_runtime.ts` (137 lines,
one per output directory, ADR 0012) and, with the contract tests, `tests/_testing.ts` (581 lines; its source is
`capabilities/generation/src/core/testing/_testing.ts`, embedded as text, ADR 0020 D4). The generated test modules,
`_register.ts` and `tests/index.ts` import it as `./_testing.js`.

**Decision.** *Decided by the maintainer:*

- The runtime stays copied: production code does not depend on domaintrail.
- The testing support becomes a package, `@domaintrail/testing`, a dev dependency of the user's project. Generated tests
  import it instead of `./_testing.js`, and `tests/_testing.ts` is no longer written. The generated code states the
  version of the package it needs, and the package is released with domaintrail, with the same version.

**Why.** The testing support is code, not something derived from the model: a fix to it should reach users by
updating a dependency, not by regenerating, and 581 lines of it should not sit in every user's repository. The runtime
is small and on the production path, where a dependency on the tool is not wanted.

**Compatibility.** Breaking (G5): a project with contract tests adds the dev dependency, and code that imported
`tests/_testing.ts` (directly or through `tests/index.ts`) imports the package.

**Rejected.**

- Copy both (the state today): bugs are fixed only by regenerating, and large files sit in users' repositories.
- Package both: production code would depend on the tool, and a runtime of another version than the generated code
  would be a skew found at run time.
- Trim the copy: smaller, but still copied and still fixed only by regenerating.

### 6. The context parameter of a factory stays required

**Today.** The factory of a verified type with `for X?` takes `context: X | undefined` (ADR 0023), so a call with no
context passes `undefined` explicitly:

```ts
export type MakeAvailableEmail = (value: Common.EmailAddress, context: CustomerId | undefined) => Promise<Result<AvailableEmail, EmailTaken>>;
const available = await makeAvailableEmail(address.value, undefined); // a new customer: no one to leave out
```

**Decision.** *Decided by the maintainer:* kept. ADR 0023 and the factory's doc comment say why: with an optional
parameter, a call that forgot the context would compile, and the check would then not leave out the one it should —
`changeEmail` would report a customer's own address as taken.

**Compatibility.** Same behaviour (G4): a doc comment.

**Rejected.**

- An optional parameter (`context?: CustomerId`): a missed ID compiles, and silently reports a customer's own address
  as taken.
- A named value for "no context" (`'none'`): as safe as `undefined`, but heavier, and one more thing to learn per
  factory.

### 7. Command parameters as one object

**Today.** Command parameters are positional, after the aggregate:

```ts
export type PlaceOrder = (id: OrderId, customer: CustomerId) => Result<…>;
export type CancelOrder = <S extends DraftOrder | ConfirmedOrder>(order: S, reason: CancelReason) => …;
export type CancelOrderDecision = { readonly Draft: (order: DraftOrder, reason: CancelReason) => …; … };
```

TypeScript has no named arguments: two parameters of one type can be swapped without an error (`issue(id, order,
billedAmount)` with two IDs), and reordering parameters in `.dt` breaks every caller.

**Decision.** *Decided by the maintainer:* a command takes its parameters as one object, after the aggregate. A command
without parameters takes none.

```ts
export type PlaceOrder = (params: { readonly id: OrderId; readonly customer: CustomerId }) => Result<…>;
export type CancelOrder = <S extends DraftOrder | ConfirmedOrder>(order: S, params: { readonly reason: CancelReason }) => …;
export type CancelOrderDecision = { readonly Draft: (order: DraftOrder, params: { readonly reason: CancelReason }) => …; … };

orderCommands.place({ id, customer });
orderCommands.cancel(order, { reason });
decide<Sales.CancelOrderDecision>(Sales.OrderShape, { Draft: (order, { reason }) => …, … });
orderCommands.archive(order); // a command without parameters
```

The contract tests draw the parameters as a record (`fc.record({ reason: a.CancelReason })`), and the examples of
commands (`Examples.<Aggregate>.commands`, typed `Parameters<…>`) become `[order, { reason }]`. The input of a policy's
command (ADR 0022) is already an object keyed by the parameters' names: for a factory it is the parameters object as
it is.

**Why.** Names at the call site: a swap is a type error or visibly wrong, and reordering in `.dt` breaks nothing. The
runtime cost, one small object per call, is negligible next to what a command allocates (the result, the aggregate, the
events) and the I/O around it.

**Compatibility.** Breaking (G6): every command implementation, decision, call and command example changes.

**Rejected.**

- Positional (the state today).
- An object only above a number of parameters: adding a parameter changes the shape of every call, and there are two
  shapes to remember.
- A choice per declaration in `.dt`: the model describes the domain, not calling conventions, and the reader must look
  up which form each command uses.

### 8. Arbitraries for recursive types

**Today.** M012 lets value objects and unions be recursive (ADR 0027, T11), but the contract tests generate no values of
them: `untestedTypes` leaves out the recursive types and every type that needs one, `dt generate ts` warns, and the
commands and required policies with such an input have no cases.

**Decision.** *Decided by the maintainer:* the contract tests draw recursive values with `fc.letrec`, biased towards
shallow values (`depthSize: 'small'`), up to a maximum depth:

```jsonc
"generate": {
  "ts": {
    "tests": {
      "maxRecursionDepth": 4, // the default
      "types": { "Modeling.Expr": { "maxRecursionDepth": 3 } }, // per type, by qualified name
    },
  },
},
```

- `generate.ts.tests.maxRecursionDepth`, default 4: a binary tree of depth 4 has at most 15 nodes.
- Overridable per type with `generate.ts.tests.types["<Ctx>.<Type>"].maxRecursionDepth`.
- Types on one cycle (`Expr` and `Call`, each holding the other) are defined together, in one `fc.letrec`.
- The warning and the left-out cases go. A type whose invariants reject too many drawn values is overridden with the
  `arbitraries` option, as any other (ADR 0020 D3); the guide says how.

**Why.** Recursive types are allowed and used (Modeling's own model); commands taking them should be tested like the
others. Shallow values keep runs fast and counterexamples small; the depth is a setting because how deep a tree must be
to exercise the rules depends on the model.

**Compatibility.** Additive (G7, after G5: the arbitraries are built with the testing package).

**Rejected.**

- No tests for recursive types (the state after ADR 0027's T11).
- Other names for the setting: `maxDepth` (depth of what?), `maxNestingDepth` (reads as any nesting, of lists and
  records too), `recursion: { maxDepth }` (a group for one setting).

### 9. A context imported from another package

**Today.** `generate.ts.contexts.<Ctx>.out` writes a context to another directory, but generated modules import each
other by relative path (`import type * as Common from './Common.js'`), which crosses package boundaries (ADR 0027). So
a package cannot use a context another package generates: Modeling's `.dt` copies the kernel's `Location` structurally
(`contexts/modeling/model/context.dt`).

**Decision.** *Decided by the maintainer:* a context may be imported instead of generated:

```jsonc
// the context's and the module's names are illustrative
"generate": { "ts": { "contexts": { "Kernel": { "import": "@domaintrail/kernel" } } } }
```

- `generate.ts.contexts.<Ctx>.import: "<module>"`, next to `out`. The context's `.dt` is read and checked with the
  others; nothing is written for it; generated code imports it from the module (`import type * as Kernel from
  '@domaintrail/kernel'`). The module is that context's generated code, published by its own package.
- The kernel describes itself in `.dt` as a shared context, and Modeling uses its `Location` instead of a copy.

**Why.** A context shared across packages is described once, and its users get its types, not a copy that may drift.

**Compatibility.** Additive (G8): a new key.

**Rejected.**

- An `out` per context with relative imports between them: the paths cross package boundaries, which ADR 0027 forbids.
- Keeping structural copies (the state today): two descriptions of one type, kept equal by hand.

### 10. Infrastructure failures in the factories of verified types

**Today.** ADR 0023 says what a factory returns — the verified value or one of its `errors` — but not what it does
when the check cannot be made: the repository is down, the outside service times out. A rejected promise escapes the
`Result`, and TypeScript cannot type it.

**Decision.** *Decided by the maintainer:* stated, types unchanged. A rejected promise means the check could not be
made (infrastructure); the errors of the `Result` are the domain's, those named in `errors`. As for policy handlers
(ADR 0022), whose rejected promise means the input cannot be computed now. The factory's doc comment says it, and the
guide shows a use case handling a rejection at its edge (the HTTP handler or the job runner: an error response, a
retry).

**Why.** A domain error is an answer the model names, and callers branch on it; an infrastructure failure is not an
answer, its kinds are open-ended, and what to do with it (retry, fail the request) is the application's edge's, not
the domain's.

**Compatibility.** Same behaviour (G4): doc comments and the guide.

**Rejected.**

- Infrastructure errors in the `Result` (`Result<AvailableEmail, EmailTaken | Unavailable>`): every caller must handle
  a case the domain does not decide, and the list of infrastructure failures is open-ended.
- An effect type (Effect-TS's `Effect<A, E, R>`): forces every user into it, and even effect systems keep untyped
  defects for failures nobody lists. Haskell's `IO` types effects, not failures: `Promise<Result<A, E>>` already
  matches `IO (Either E A)`.

## Amends

- [ADR 0001](0001-mvp-implementation-decisions.md), TypeScript representations: `id X: UUID` keeps its type, but its
  constructor checks the form (decision 1). `UUID` as a plain field stays `string`.
- [ADR 0003](0003-domain-primitives.md), Generated TypeScript: "Without invariants the constructor cannot fail" no
  longer holds for an ID or primitive on `UUID` (decision 1).
- [ADR 0020](0020-generated-checks-and-contract-tests.md): D1 gains `check<Aggregate>Common` (decision 2) and the
  `'uuid'` invariant of IDs and primitives on `UUID` (decision 1); D3 draws recursive values (decision 8) and command
  parameters as records (decision 7); D4 and Layout: the generic helpers are the package `@domaintrail/testing`, not
  `tests/_testing.ts` (decision 5), and `generate.ts.tests` gains `maxRecursionDepth` and `types` (decision 8).
- [ADR 0023](0023-verified-types.md), Generated TypeScript: why the context parameter is required (decision 6), and
  what a rejected promise of a factory means (decision 10).
- [ADR 0027](0027-domain-and-application-boundaries.md), Implementation notes: the rule `generated` ("a package's
  generated code imports only its own files") lets generated code import an imported context's module (decision 9);
  two items of "Left for later" are done (values of recursive types, the kernel's `Location` imported).
- The examples of command types in ADR 0018 and 0019 (`ConfirmOrder = (order: DraftOrder, at: Timestamp) => …`) show
  positional parameters; the generated code takes an object (decision 7). Their text is not rewritten.

## Details left to the tasks

The maintainer decided the points above. These details follow from them but were not decided one by one; the shapes
written above are the expected ones, and the task settles each, recording a different choice in its pull request:

- G1: the exact form accepted as a UUID (the 8-4-4-4-12 hexadecimal form in either case, any version, is expected, so
  that `crypto.randomUUID()` and UUIDv7 both pass); the place of `'uuid'` among the invariants (first is expected);
  what happens when a type declares an invariant of its own named `uuid`.
- G2: whether `check<Aggregate>Common` is also written when the aggregate has states but no invariants of its own.
- G3: the names of the generator's own temporaries (`$0` in `contains`), which no `.dt` names; what counts as a clash
  for a lambda variable (another variable in scope, the check's parameter, a reserved word, a name the module
  imports).
- G4: a `{@link}` to a context the module does not otherwise import.
- G5: where the package lives in the workspace and how it is published (`docs/releasing.md`); how the generated code
  states the version it needs and what reports a mismatch; whether fast-check becomes a peer dependency of the
  package; what `tests/index.ts` re-exports; removing a `tests/_testing.ts` left by an earlier version.
- G6: the name of the parameters object in the generated types; how an optional parameter is typed in it (a required
  key `note: string | undefined`, for the reason of decision 6, or an optional property); whether the requirement
  checks (`check<Command>Requires(aggregate, …params)`, ADR 0020 D1) take the object too.
- G7: the depth used for a cycle of types whose per-type settings differ.
- G8: whether `import` excludes `out` and `policies`; how the contract tests of a context using an imported one get
  its arbitraries (today they import the other context's `tests/<Ctx>.ts`, which is not generated for an imported
  context); how the kernel's hand-written types and its `.dt` stay one.

## Consequences

- Three breaking changes (G1, G5, G6) in one release, with the changelog stating each and what to change: handle the
  `Result` of `make<Id>` and use UUIDs in fixtures; add `@domaintrail/testing`; pass command parameters as an object.
- The generated checks read like the model, once per invariant; references are navigable.
- Contract tests reach recursive types, and a project with contract tests depends on a package released with
  domaintrail, at the same version.
- A context can be described in one package and used by others through `.dt`; Modeling's copy of `Location` goes.
- What a factory's failure means is written down, for factories and policy handlers alike: the domain's answers in the
  `Result`, the infrastructure's in the rejection.
